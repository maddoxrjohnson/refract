# 18. A refactor runs in its own worktree, in plan mode, and merges only on request

Status: accepted

**Context.** Refract launches agents, and a common job to give one is "tidy this repo up": remove duplication, split oversized files, delete dead code. Doing that in the repo you are working in is risky. It collides with uncommitted changes and with an agent already running there, a half-done refactor sits in the working copy, and undoing it means digging through your own edits. The job should be one button, but the person must stay in charge of what lands on their branch.

**Decision.** Refactor creates a git worktree of the repo on a new `refactor/<yyyymmdd-hhmm>` branch, starting from the repo's last commit, under `~/projects/.refract-worktrees/`. It opens that worktree in its own VS Code window and starts Claude there in plan mode, with a built-in prompt and an optional "Focus on…" line, using the default model. The agent installs dependencies, runs the repo's checks for a baseline, and proposes up to three behaviour-preserving refactors. The person approves or edits the plan in the terminal. The agent then makes one commit per refactor, re-runs the checks after each, and reverts a refactor that breaks a check that passed in the baseline. It reports the checks and a summary in a result file in the worktree's git directory.

The repo gets one refactor at a time. When it is done the panel shows commits, diffstat and checks, and offers Review in VS Code, Merge and Discard. Merge rebases the branch onto the target branch if that moved on (aborting and offering "Fix with Claude" on a conflict), then fast-forwards the target with `--ff-only` (or `git fetch . branch:target` when the target is not checked out), then removes the worktree and branch without `--force`. Refract refuses to merge when the agent is working, when an uncommitted file in the repo is one the refactor changed, when another worktree has the target, or when the target no longer holds the commit the refactor started from. Discard is the only path that forces. Nothing is pushed, and a worktree is deleted only if it lies under the Refract worktrees folder and is listed by the repo's `git worktree list`.

**Consequences.** The working copy and any running agent are untouched until the final fast-forward, so a repo can be refactored while it is busy; the dialog only notes the commit it starts from and how many uncommitted files are left out. The agent starts from a clean checkout, so it must install dependencies itself, and a large project can take a while to set up. Records in `~/.local/state/refract/refactors/` let a refactor survive a restart; on start the helper reconciles them with `git worktree list`, so a deleted worktree drops its record and a stray `refactor/` worktree is adopted. A refactor needs a branch and a commit: a detached HEAD or an empty repo is refused, and a remote-only repo has no button. Because plan approval is a terminal prompt, the stone and a toast need the status hook to say when the agent is waiting; without it the refactor still works, but nothing signals that the plan is ready. The branch is local until the person pushes it by hand. A merge can fail for reasons the person has to clear (a busy target, a dirty overlap), each named in the panel with the files involved.

**Alternatives considered.**
- **Refactor in the working copy.** Simpler, but it collides with uncommitted work and running agents, and a failed attempt has to be unpicked by hand. Rejected for the data-safety reasons above.
- **An autonomous run with no plan step.** Fewer clicks, but the person would find out what changed only afterwards, and a refactor's value depends on the choice of what to change. Plan mode makes approval the one required interaction.
- **A separate stone for each worktree.** It would show the refactor in the scene, but clutters it with a stone that is the same repo, and the search already skips dot directories. The parent stone carries a refactor mark and its panel shows the state.
- **A diff viewer in Refract.** Reviewing is what VS Code is for, and a viewer would be a large new surface. The panel shows the summary and opens the worktree's window instead.
