# 19. Linked worktrees fold into their repo, and Remove keeps the branch

Status: accepted

**Context.** A linked git worktree is a second checkout of the same repo, usually on another branch, and agents make them often: to keep a change apart from other work in progress, or because a project's instructions ask for isolated worktrees. Refract found each one as a repo and drew it as a second stone with nearly the same name, which read as a duplicate. Deciding whether a worktree was still needed meant checking by hand whether it had uncommitted changes, whether its commits were pushed, merged or released, and what the agent there last said, sometimes in an old transcript that ended with an unanswered question.

**Decision.** The helper keeps tracking each linked worktree as a repo, so sessions, launch, the status hook and refresh work unchanged, and adds `worktreeOf` and `worktree` facts to its snapshot. It also finds the linked worktrees of known repos outside the roots and nested inside them. The app folds a worktree into its main repo's stone when that repo is shown: the stone gets a checkout-count mark and the most urgent agent state of the group, and the panel lists each worktree with a status that answers "am I done with this?", the last agent message, Open, and Remove. Remove runs `git worktree remove` without `--force` and never touches the branch. It is offered only when the worktree is clean (untracked files too), its commits are on a remote or merged, no agent is open in it and nothing else is nested inside it, and the helper re-checks all of this when it runs. Refract's own refactor worktrees stay with the Refactor flow.

**Consequences.** One stone per repo, and the question that prompted this is answered at a glance: a finished worktree reads "In v0.13.3 · Ready to remove". The helper does a little more work for linked worktrees only: a few ref queries with each HEAD refresh, and, for a worktree that could be removed, an ignored-file listing and a bounded search for nested repos. Ordinary repos pay one file check. Removal is conservative: an idle open agent, a submodule, a nested repo or an uncountable history all keep the folder, and each says why. Squash and rebase merges aren't recognised as merged and read "Pushed, not merged", which still allows Remove. Worktrees on Windows drives show their status but can't be removed from Refract yet. Build and dependency folders aren't searched for nested repos, so a plain repo kept inside `node_modules` or `target` isn't seen; the confirm still lists those folders as being deleted.

**Alternatives considered.**
- **Small satellite stones per worktree.** More visible, but it brings back the clutter of near-duplicate stones and needs more scene work. The panel carries the detail; the mark says there is more.
- **Keep separate stones, labelled.** The smallest change, but it doesn't help with deciding when a worktree is finished.
- **Fold in the helper, sending one snapshot per repo.** It would hide worktrees from every part of the protocol, but launch, resume, focus, sessions and the status hook are all keyed by a repo path, and each would need a worktree path added. Folding in the app kept all of that working.
- **Also delete the branch.** Convenient once a branch is merged, but deleting a branch is a different kind of loss than deleting a clean checkout, and the person may still want it. Not offered.
